# 家庭成员读口径统一方案（审查⏳2 · 2026-09-09）

## 一、问题

家庭成员（非 owner）访问共享宠物时，**统计与 AI 分析类读路径返回空**。根因：仓储层查询同时按 `pet_id = $1 AND user_id = $2` 过滤——`user_id` 是宠物 owner，成员的 userId 对不上，行被过滤光。

## 二、影响面盘点（已 grep 取证）

| 类别 | 文件（repo 层带 `pet_id AND user_id` 双条件） | 现状 |
| --- | --- | --- |
| 趋势 | trendRepository（日聚合/区间统计） | 成员看共享宠趋势为空 |
| 症状/慢病/喂养 | symptomRepository / chronicRepository / feedingRecordRepository | 成员看为空 |
| 疫苗/时光线/素材 | vaccineRepository / timelineRepository / petFactRepository / suggestionRecordRepository | 成员看为空 |
| 头像库 | avatarRepository | 成员看为空 |
| **已正确** | checkinRepository（findTodayCheckin 仅按 pet_id）、petRepository（canAccess 双表 UNION） | 打卡走 pet 维度 ✅ |

路由层归属校验现状：owner 专属操作走 `checkPetOwnership`（正确），成员可访问走 `checkPetAccess`（canAccess 正确）——**问题只在 repo 层数据行过滤**，不在权限层。

## 三、方案（pet 维度化）

**统一口径：权限层判断「能不能看这只宠」（canAccess，owner 或家庭成员），数据层只按 `pet_id` 过滤行，删除 `user_id` 条件。**

1. **仓储层**：受影响 repo 方法去掉 `AND user_id = $n` 参数（约 10-14 个方法）。
   - 保留 user_id 过滤的例外：**隐私敏感的跨宠物聚合**（如 feedingRepository.countByUser 按 user 统计查询次数）不动——它们本来就是用户维度统计而非宠物数据。
2. **路由层**：消费这些 repo 的路由必须挂在 `checkPetAccess`（成员可读）之后，owner-only 动作（删除/编辑）维持 `checkPetOwnership` 不变。
3. **AI 分析链路**：symptomAi/chronicRisk/feedingAi 的取数函数同步去 user_id 条件（它们从 repo 取数，repo 改完自动生效，仅需核对入参）。
4. **测试**：每个改动方法补「成员访问共享宠返回数据」用例；存量断言同步。

## 四、实施边界与风险

- 工作量：约 8-10 文件 + 路由核对 + 测试，**专项一轮**（不宜夹带）。
- 风险：去 user_id 条件后，越权面由「权限层 checkPetAccess 单点把关」——需在改造时逐路由确认挂了 checkPetAccess（现已有，风险低）。
- 兼容：无 schema 变更、无 API 契约变更（响应结构不变，成员从空变有数据）。

## 五、建议排期

验证期（R1 收尾后、R2 启动时）作为独立专项实施；家庭成员共同养宠是既定产品能力（家庭墙/周报已支持），读口径统一是其补完。
