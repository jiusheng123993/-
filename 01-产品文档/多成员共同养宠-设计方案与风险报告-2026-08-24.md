# 多成员共同养宠 · 设计方案与风险报告

> 日期：2026-08-24
> 状态：待用户确认后开发
> 背景：用户提出"情侣养宠物/家庭养宠物"场景——当前星河宠记宠物档案归属单一用户，需要支持多成员共管。

---

## 一、目标与用户场景

### 1.1 目标
支持**情侣 / 家庭成员共同养宠**：同一只宠物由多个用户共同查看、共同打卡记录、共同参与健康管理，家庭周报/AI 分析纳入所有成员的数据。

### 1.2 典型场景
- 情侣养一只猫：双方都能看到宠物档案、都能打卡、都能写回忆；周报显示"这周 TA 打卡 3 次、我打卡 2 次"
- 家庭养一只狗：孩子记录喂食、家长记录疫苗，家庭动态墙展示所有人对宠物的照顾
- 新成员加入：扫描/点击邀请 → 加入家庭 → 看到宠物 → 开始共同记录

---

## 二、现状盘点（已核实）

### 2.1 已有能力（可复用）
| 能力 | 位置 | 说明 |
|---|---|---|
| 家庭主表 `pet_families` | DB | `id + user_id`（**单一创建者**）+ name/avatar |
| 宠物-家庭关联 `pet_family_members` | DB | `family_id + pet_id + role`（**成员=宠物**，非"人"） |
| 家庭动态墙 `pet_family_feeds` | DB | 带 `user_id`（记录人），已支持"谁记录的" |
| 家庭周报 `pet_family_weekly_reports` | 服务 | 已通过 `pet_family_members` JOIN **聚合家庭所有宠物**的打卡/症状 |
| 家庭排行/角色 | 服务 | leaderboard + 角色分配 |
| 家族图谱/家庭照片/家庭日历 | 服务 | familyTree/familyPhotos/dashboard |
| 邀请码/分享 | 服务 | invite_codes + referral_records（裂变推荐） |
| 打卡/疫苗/症状/回忆记录 | DB | **均带 `user_id`**（记录人字段天然存在） |

### 2.2 核心缺口（本次要解决）
1. **"人"不在家庭里**：`pet_family_members` 关联的是宠物，**没有"家庭成员用户"表**；家庭操作校验 `findByIdAndUser(familyId, userId)` 只认创建者
2. **宠物档案单 owner**：`pet_profiles.user_id` 唯一；`petRepository.isOwner / findByIdAndUser / findAllByUser` 全部按单一 owner 校验 → 家庭成员**看不到、更无法操作**对方宠物
3. **前端单人叙事**：首页/宠物 tab 是"我的宠物"，无"共同养宠"入口与标识
4. **记录归属展示弱**：打卡有 user_id 但界面不显示"谁记录的"

## 三、核心设计

### 3.1 数据模型（新增 1 张表，不破坏现有表）

```sql
-- 家庭成员（人）关联表：家庭 ←→ 用户
CREATE TABLE IF NOT EXISTS pet_family_users (
  id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  family_id  UUID NOT NULL REFERENCES pet_families(id) ON DELETE CASCADE,
  user_id    UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  role       TEXT NOT NULL DEFAULT 'member' CHECK (role IN ('owner', 'member')),
  joined_at  TIMESTAMPTZ DEFAULT NOW(),
  UNIQUE(family_id, user_id)
);
CREATE INDEX IF NOT EXISTS idx_family_users_user ON pet_family_users(user_id);
```

- **迁移兼容**：建表时把现有 `pet_families.user_id`（创建者）回填为 `pet_family_users` 的 owner 行（`INSERT ... SELECT` 幂等）→ 老用户零感知
- **宠物访问判定**（替代单 owner `isOwner`）：

```
canAccessPet(petId, me):
  ① pet.user_id == me            → 主人（完全权限）
  ② ∃ family: pet∈family.members AND me∈family.users
      → 家庭成员（共享权限，见权限矩阵）
  ③ 否则 → 无权限
```

### 3.2 权限矩阵（核心，后端统一校验，绝不只靠前端）

| 操作 | 宠物主人（owner） | 家庭成员 | 非成员 |
|---|---|---|---|
| 查看宠物档案/记录 | ✅ | ✅ | ❌ |
| 健康打卡/症状初筛/喂食记录 | ✅ | ✅（记录 user_id=本人） | ❌ |
| 疫苗/驱虫记录 | ✅ | ✅ | ❌ |
| 写回忆/家庭动态 | ✅ | ✅ | ❌ |
| 编辑宠物档案（名字/头像/资料） | ✅ | ✅（有限字段） | ❌ |
| **删除宠物档案** | ✅ | ❌ | ❌ |
| 邀请成员/移除成员/解散家庭 | ✅（owner 专属） | ❌ | ❌ |
| 管理家庭宠物（宠物加入/移出家庭） | ✅ | ❌ | ❌ |

> 安全要点：所有宠物操作路由从 `isOwner` 升级为 `canAccessPet`；家庭管理路由从 `findByIdAndUser` 升级为 `requireFamilyOwner`（查 pet_family_users.role=owner）。删除、家庭成员管理等高危操作仅 owner。

### 3.3 接口改造清单

**后端（新增）**
- `POST /api/families/:id/members/users` 邀请成员（owner，返回邀请码/链接）
- `POST /api/families/join` 凭邀请码加入家庭（免密/或校验）
- `DELETE /api/families/:id/members/users/:userId` 移除成员（owner）
- `GET /api/families/:id/users` 成员列表（含角色）
- `GET /api/pets/shared` 我共管的宠物列表（家庭成员视角）

**后端（改造校验，复用现有路由）**
- 宠物相关：`pets`、`checkins`、`vaccines`、`symptom-checks`、`feeding`、`moments`、`chronic` 等路由的归属校验统一改为 `canAccessPet`
- 家庭相关：`feeds`、`weekly-reports`、`leaderboard`、`familyTree`、`familyPhotos` 的 `verifyFamilyOwnership` 改为 `requireFamilyMember`（成员可读）+ `requireFamilyOwner`（管理操作）

**前端**
- 宠物 tab：宠物卡显示"👥 共同养宠"标识；档案页显示家庭成员列表
- 打卡/回忆：列表标注"谁记录的"（用成员昵称/头像）
- 家庭 tab：新增"成员管理"（邀请/移除，owner 可见）；未加入家庭时引导"邀请 TA 一起养宠"
- 情侣引导：登录后/首页检测 `canAccessPet` 有共享宠物但无家庭成员时，引导绑定（复用邀请码）
- 我的页：显示我所在的家庭/共享宠物

### 3.4 周报 AI 增强（可选，二期）
现有周报已按家庭聚合宠物数据；增强为按成员维度：`user_id` 分组统计"本周每位成员打卡 N 次、贡献喂食 M 次"，AI 总结"你们一起照顾了 X"。

## 四、影响分析与风险

| 项 | 影响 | 风险等级 |
|---|---|---|
| 数据库 | 新增 `pet_family_users` 表（迁移 025）；不动现有表结构 | 中（部署需执行迁移，owner 移交按部署配置规范） |
| 权限模型 | `isOwner` → `canAccessPet`，涉及**所有宠物相关路由** | **高**（越权风险：改错一处=跨用户数据泄露；必须有完整权限矩阵测试） |
| 兼容性 | 老用户无家庭 → 判定走 owner 分支，行为不变 | 低 |
| 前端 | 宠物/家庭/首页多处 UI 改动 | 中 |
| 安全红线 | 多用户共享后归属校验必须后端统一，删除/管理仅 owner | 高（规则 5.2：禁止只靠前端隐藏控件） |

## 五、分阶段实施（单模块串行）

- **M1 数据层**：迁移 025 建表 + 回填 owner；FamilyRepository 扩展（成员 CRUD）；`canAccessPet` 权限工具
- **M2 后端权限改造**：宠物相关路由统一校验（含权限矩阵测试）
- **M3 家庭管理接口**：邀请/加入/移除/成员列表
- **M4 前端**：共管标识、记录归属、成员管理、情侣引导
- **M5 周报成员维度**（可选二期）
- 每阶段：跑测试 → 构建 → 提交；M2 结束做权限专项测试 + 双 Agent 审查

## 六、验证计划

- 权限矩阵单测：owner / member / 非成员 × 每类操作（正常+越权）
- 全量回归：后端测试 + 小程序 typecheck/测试/构建
- 部署冒烟：迁移执行、共享宠物打卡/周报聚合真实数据验证
- 双 Agent 审查：重点安全维度（越权、删除、成员管理）
