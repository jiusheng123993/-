# 星河宠记 · 宠物医学知识图谱与置信度设计方案（2026-08-22）

> 状态：待用户审阅
> 背景：用户提出——①症状初筛目前是"纯本地规则表"，担心误判；②希望接入 AI + 真实医疗数据做初步分析（类似豆包问答）；③明确红线：**不做诊断、不推荐用药，只做带免责声明的分析**；④关心能否增加分析置信度；⑤明确要求**记忆引擎必须"类人记忆、双向读写"**——既沉淀健康事件，又能在分析时召回相关过往。
> 结论先行：**不爬取数据**，将现有规则表结构化升级为"医学知识图谱（JSON 静态数据）+ 置信度/依据字段 + 记忆引擎双向接入"，规则引擎兜底、知识图谱提供依据、记忆引擎提供类人背景、LLM 只做话术包装。
> 本设计为纯文档，不涉及代码改动，供审阅后实施。

---

## 一、设计目标与边界

### 1.1 目标

1. **增加分析置信度**：让每次分析的结论"有出处、可解释、可测试"，而不是黑盒。
2. **保留安全底线**：紧急判断永远由规则引擎完成，不交给 AI。
3. **数据可维护**：把写死在代码里的规则表升级为结构化、带版本、带审核状态的知识图谱。
4. **记忆引擎类人化**：双向读写——健康事件自动沉淀（写）、症状分析时召回相关过往（读），让分析像"了解这只宠物的老熟人"一样有上下文。

### 1.2 边界（红线，任何阶段不得突破）

| 红线 | 说明 |
| --- | --- |
| ❌ 不做诊断 | 不输出"你的猫得了XX病"式结论；只输出"症状→紧急程度→建议动作" |
| ❌ 不推荐用药 | 护理建议只含观察/禁食/就医触发条件，不含任何药物名称与剂量 |
| ✅ 只做免责分析 | 所有医疗相关输出必须附带免责声明（沿用 PRD 8.4 宠物管家免责模板） |
| ❌ 不爬取数据 | 数据只来自现有资产 + 开放许可权威源 + 人工审核，不爬第三方网站 |
| 🧠 记忆只作背景 | 记忆引擎召回的记忆**不参与 riskLevel 推导**，只作展示（basis='record'） |

## 三、总体架构（三层协作 + 记忆引擎旁路）

```
┌─────────────────────────────────────────────────────────┐
│  用户选择症状（页面） / 描述症状（聊天）                     │
└─────────────┬───────────────────────────┬───────────────┘
              ▼                           ▼
┌───────────────────────────┐   ┌─────────────────────────────┐
│ 第 1 层：规则引擎           │   │ 记忆引擎（类人记忆，双向）      │
│ （安全底线，0 成本）         │   │  · 写：症状初筛/打卡异常/恢复    │
│  · RiskRule 表命中         │◀──│    事件 → health/medical 记忆  │
│  · 个性化调整（只升不降）    │   │  · 读：症状相关性召回（带闸门）   │
│  · 输出 riskLevel          │   │     → 相似病史/医嘱/季节规律    │
└─────────────┬─────────────┘   └─────────────┬───────────────┘
              ▼                               ▼
┌─────────────────────────────────────────────────────────────┐
│ 第 2 层：知识图谱 + 记忆召回（依据来源）                       │
│  · 症状→疾病关联、品种健康、护理建议、来源引用                  │
│  · 记忆闸门：category∈{health,medical} + active +             │
│    importance≥5 + 近90天 + 症状相关性                          │
│  · 生成 conclusions[]（basis = rule/graph/record/llm）        │
└─────────────────────────────┬───────────────────────────────┘
                              ▼
┌─────────────────────────────────────────────────────────────┐
│ 第 3 层：LLM 深度分析（会员专属，可选增强）                     │
│  · 注入：图谱命中条目 + 宠物档案 + 近7天打卡 + 召回记忆          │
│  · LLM 只做"话术组织"，判断依据全部来自图谱与记忆               │
│  · 输出再过 guardOutput 安全检测                              │
└─────────────────────────────┬───────────────────────────────┘
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  合并输出：riskLevel + conclusions + confidence + 免责声明     │
└─────────────────────────────────────────────────────────────┘
```

**分工原则**：
- 规则引擎负责"对错"（安全底线，永不绕过，记忆不得参与 riskLevel 推导）
- 知识图谱负责"依据"（每个结论都有出处）
- 记忆引擎负责"背景"（类人记忆：双向读写，只作展示不作判断）
- LLM 负责"温度"（把依据讲成人话），且永远在安全检测之下

### 3.1 职责边界：谁拍板、谁分析（重要澄清）

用户疑问："规则引擎做不了初筛，顶多给去医院建议。"——确认：**规则引擎确实做不了"分析型初筛"，它做的是"分诊型初筛"**，而这正是 PRD 4.5 对"初筛"的定义（评估紧急程度 + 建议是否就医）。"去医院建议"不是规则引擎的"顶多"，而是它守住的"底线"。

| 初筛职责 | 谁来做 | 依据 | 容错要求 |
| --- | --- | --- | --- |
| 急诊识别（抽搐/呼吸困难→立即就医） | 规则引擎（拍板） | RiskRule 表 | 100% 确定，零容错 |
| 紧急分级（红/橙/黄/绿） | 规则引擎（拍板） | RiskRule 表 | 确定性、可测试 |
| 是否就医建议 | 规则引擎（拍板） | RiskRule 表 | 保守优先（只升不降） |
| "可能是什么方向"（胃炎？食物不耐受？） | 知识图谱（分析） | Disease 关联 | 提示排查，不做诊断 |
| 结合宠物历史讲背景 | 记忆引擎（分析） | 记忆召回 | 只作展示，不进 riskLevel |
| 组织话术、讲人话 | LLM（分析） | 图谱+记忆注入 | 输出过 guardOutput |

**拍板权唯一性**：riskLevel（该不该去医院）只能由规则引擎产出；图谱/记忆/LLM 全部是"分析层"——可以丰富解释、可以升级提示（只升不降），但永远不能降低或改写规则引擎的 riskLevel。

## 四、知识图谱数据结构（核心设计）

### 4.1 存储形态

- **静态 JSON/TS 数据文件**（MVP 不引图数据库，与 PRD 9.1"JSON知识库→本地查询"一致）
- 建议路径：`小程序/miniapp/src/data/petKnowledge/medicalGraph.ts`（与 breeds/foodSafety 同目录）
- 每个实体带 `sourceRef` + `reviewStatus`，保证"无来源不收录"

### 4.2 基础类型

```ts
/** 身体系统枚举：用于症状归类与疾病关联 */
type BodySystem =
  | 'digestive' | 'respiratory' | 'skin' | 'urinary'
  | 'nervous' | 'behavior' | 'eye_ear_mouth'
  | 'cardiovascular' | 'endocrine'

/** 紧急程度：与现有 symptomService.riskLevel 完全对齐，避免双套语义 */
type RiskLevel = 'normal' | 'caution' | 'warning' | 'emergency'

/** 结论依据类型：rule=规则命中 / graph=图谱条目 / record=宠物记录(含记忆召回) / llm=AI推断 */
type EvidenceBasis = 'rule' | 'graph' | 'record' | 'llm'

/** 置信度：由规则推导得出，禁止 LLM 自评 */
type Confidence = 'high' | 'medium' | 'low'

/** 审核状态：draft=待审 / reviewed=已核 / rejected=驳回 */
type ReviewStatus = 'draft' | 'reviewed' | 'rejected'

/** 来源权威度：authoritative=权威机构 / community=社区整理 / internal=内部自审 */
type Authority = 'authoritative' | 'community' | 'internal'
```

### 4.3 核心实体

```ts
/** 依据来源引用：置信度的"底气"，所有图谱条目必须挂来源 */
interface EvidenceSourceRef {
  sourceId: string              // 来源 ID（如 'merck' / 'aspca' / 'akc' / 'wsava' / 'self_reviewed'）
  title: string                 // 来源标题（如 'Merck Veterinary Manual'）
  url?: string                  // 原文链接（可公开访问则给出）
  authority: Authority          // 权威度（决定置信度上限）
  reviewedAt?: string           // 最近人工审核时间（YYYY-MM-DD）
  reviewStatus: ReviewStatus    // 审核状态（draft 条目不允许进入正式输出）
}

/** 症状实体：与现有 symptomService 的 symptomId 对齐（如 'vomiting'） */
interface SymptomEntity {
  id: string                    // 症状 ID（沿用现有 ID，零迁移成本）
  name: string                  // 症状名（'呕吐'）
  description: string           // 症状描述（供用户核对，减少误选导致的误判）
  species: ('cat' | 'dog')[]    // 适用物种
  bodySystem: BodySystem        // 所属身体系统
  urgencyHints?: string[]       // 天然紧急提示（如抽搐→"疑似神经系统急症，立即就医"）
}

/** 风险规则：替代写死的 EMERGENCY_SYMPTOMS / WARNING_SYMPTOM_COMBOS / CAUTION_SYMPTOMS */
interface RiskRuleEntity {
  id: string                    // 规则 ID（如 'rule_vomit_lethargy_emergency'）
  name: string                  // 规则名（'呕吐+精神差 → 紧急'）
  level: RiskLevel              // 命中后紧急程度
  priority: number              // 匹配优先级（大数优先：先查紧急、再查组合、最后单症状）
  match: {
    type: 'single' | 'combo' | 'with_condition'
    symptomIds: string[]        // 命中症状（单症状或组合）
    conditions?: {              // 附加条件（可选）
      durationIn?: string[]     // 持续时长命中项（如 ['2-3天', '3天以上']）
      appetite?: string         // 食欲状态（'decreased'）
      energy?: string           // 精神状态（'low'）
    }
  }
  sourceRef: EvidenceSourceRef  // 规则依据来源
}

/** 可能疾病：只做"提及/提示排查"，绝不做诊断结论 */
interface DiseaseEntity {
  id: string                    // 疾病 ID（如 'gastritis'）
  name: string                  // 疾病名（'胃炎'）
  species: ('cat' | 'dog')[]
  relatedSymptoms: Array<{      // 症状关联（带强度权重）
    symptomId: string
    weight: 1 | 2 | 3           // 3=高度相关（如呕吐→胃炎），1=弱相关
  }>
  typicalText: string           // 一句话中性科普（如"胃炎常见于进食不规律或误食刺激性食物后"）
  emergencyLevel: RiskLevel     // 该疾病本身的紧急提示（用于个性化 insights，不构成诊断）
  sourceRef: EvidenceSourceRef
}

/** 护理建议：只含观察/禁食/就医触发，严禁含药物 */
interface CareAdviceEntity {
  id: string                    // 建议 ID
  scenario: string              // 适用场景（'轻微呕吐，精神食欲正常'）
  level: RiskLevel              // 适用紧急程度
  actions: string[]             // 观察/护理动作（如 ['先禁食4-6小时观察']，不含药物）
  observeFor: string            // 观察时长（'24小时'）
  vetTrigger: string            // 触发就医条件（'呕吐超过24小时 或 出现精神差'）
  disclaimer: string            // 免责声明（引用 PRD 8.4 模板）
  sourceRef: EvidenceSourceRef
}

/** 品种健康档案：由 breeds.ts 派生，补充疾病风险等级 */
interface BreedHealthEntity {
  breedId: string               // 对应 breeds.ts 的 id
  species: 'dog' | 'cat'
  geneticDiseases: Array<{      // 遗传病易感（带权重）
    diseaseId: string
    weight: 1 | 2 | 3
  }>
  ageRisk: {                    // 年龄阶段风险提示
    stage: 'puppy' | 'senior'
    note: string                // 如 '金毛老年期髋关节问题高发，注意步态变化'
  }
  sourceRef: EvidenceSourceRef
}

/** 医学知识图谱整体（单文件静态数据，带版本号） */
interface MedicalKnowledgeGraph {
  version: string               // 图谱版本（如 '2026-08-22.1'，审核更新时递增）
  updatedAt: string             // 更新时间
  sources: EvidenceSourceRef[]  // 来源注册表
  symptoms: SymptomEntity[]
  riskRules: RiskRuleEntity[]
  diseases: DiseaseEntity[]
  careAdvice: CareAdviceEntity[]
  breedHealth: BreedHealthEntity[]
}
```

### 4.4 关系说明（逻辑关系，JSON 用外键表达，不引图数据库）

```
Symptom ──relatedSymptoms──▶ Disease ──emergencyLevel──▶ RiskLevel
Symptom ──match.symptomIds──▶ RiskRule ──level──▶ RiskLevel
Disease ──scenario──▶ CareAdvice（按 RiskLevel 关联）
Breed ──geneticDiseases──▶ Disease（品种易感）
所有实体 ──sourceRef──▶ EvidenceSourceRef（审核状态）
记忆召回 ──basis='record'──▶ conclusions（见第六章）
```

## 五、置信度模型（核心设计）

### 5.1 置信度推导规则（纯代码推导，禁止 AI 自评）

AI 自评的置信度（"我觉得有 95% 把握"）是最不可信的，因此置信度由**代码根据依据类型 + 来源权威度**推导：

| 场景 | basis | confidence | 说明 |
| --- | --- | --- | --- |
| 命中紧急规则（如抽搐/呼吸困难） | rule | high | 底线规则，来源权威，无歧义 |
| 命中知识图谱条目且来源权威（authoritative）、关联权重=3 | graph | high | 有权威出处 + 强关联 |
| 命中知识图谱一般条目（权重 1-2）或来源为 community/internal | graph | medium | 有依据但关联强度或权威度一般 |
| 依据宠物记录/召回记忆（近7天打卡异常、历史症状复发、记忆引擎 health/medical 召回） | record | medium | 真实数据但非医学结论；记忆类结论固定 medium 且标注来源"日常记忆" |
| 图谱无条目，LLM 根据注入上下文推断 | llm | low | 明确标注"AI 推测，仅供参考" |

**整体置信度 = 所有结论中最低的一档（保守原则）**——只要有一条结论是 `low`，整体就提示用户"部分内容为推测"。

**记忆约束（关键）**：记忆/打卡类 `record` 依据**只能作为背景信息展示，不得参与 riskLevel 推导**——安全底线由规则引擎独占。若记忆命中"医嘱/慢性病"且与当前症状相关，仅触发"建议就医"提示（符合只升不降原则，见 6.6）。

### 5.2 结论结构（输出给前端/LLM 的统一格式）

```ts
/** 单条分析结论：每个结论都带依据 + 置信度 */
interface AnalysisConclusion {
  text: string                  // 结论文案（如 '呕吐+精神差属于高风险组合，建议24小时内就医'）
  basis: EvidenceBasis          // 依据类型
  confidence: Confidence        // 置信度（代码推导）
  evidence?: string             // 展示给用户的依据文字（如 '依据：Merck Veterinary Manual 症状映射'）
  sourceRef?: EvidenceSourceRef // 完整来源引用（前端可展示来源徽标）
}

/** 症状分析结果（在现有 SymptomCheckResult 上扩展） */
interface SymptomAnalysisResult {
  riskLevel: RiskLevel          // 紧急程度（规则引擎输出，行为不变）
  confidence: Confidence        // 整体置信度 = 所有结论最低档
  conclusions: AnalysisConclusion[]
  possibleConditions: string[]  // 保留现有字段（仅为"提示排查"，非诊断）
  personalizedInsights: unknown[]  // 保留现有个性化洞察（含记忆召回类）
  disclaimer: string            // 免责声明（PRD 8.4）
}
```

### 5.3 前端展示设计（置信度可见化）

```
┌──────────────────────────────────────────┐
│ 🟠 建议24小时内就医          置信度: 高    │
│                                        │
│ 分析结论：                              │
│ · 呕吐+精神差为高风险组合      [依据:图谱] │ ← 每条带来源徽标
│ · 近3天打卡连续异常            [依据:记录] │
│ · 品种：金毛老年期关节问题风险 [依据:图谱] │
│ · 可能是XX（AI推测）          [依据:AI] 🤖 │ ← low 结论明确标注"推测"
│ · 📋 上次3月也吐过，3天恢复    [依据:记忆] │ ← 记忆召回类（record）
│                                        │
│ ⚠️ 本建议仅供参考，不替代专业兽医诊断。   │
└──────────────────────────────────────────┘
```

**设计要点**：置信度不是一句"AI 很准"的宣传，而是让用户**看见每条结论的依据**，自己权衡。`low` 结论必须带 🤖 标记与"推测"字样；记忆类结论带 📋 标记与"日常记忆"字样。

## 六、记忆引擎双向接入（类人记忆）

用户明确要求：记忆引擎必须"类人记忆、双向读写"——既能沉淀健康事件（写），又能在分析时召回相关过往（读），让分析像"了解这只宠物的老熟人"一样有上下文。

### 6.1 双向闭环

```
┌─────────────── 写（记忆沉淀，已有+补齐） ───────────────┐
│ 症状初筛 → medical 记忆（已有：symptoms.ts L60）         │
│ 打卡异常 → health 记忆（已有：memoryService.recordHealthMemory）│
│ 恢复事件 → "XX症状已恢复，历时N天" 记忆（新增：补齐闭环）   │
└──────────────────────────────────────────────────────┘
                      ▲ 沉淀
                      │
              用户健康行为（打卡/症状初筛/聊天）
                      │
                      ▼ 召回
┌─────────────── 读（记忆召回，新增·带闸门） ───────────────┐
│ 症状相关性召回 → basis='record' insights                 │
│ 相似病史 / 医嘱关联 / 季节规律 / 恢复参考                 │
│ 只作背景展示，不参与 riskLevel 推导                      │
└──────────────────────────────────────────────────────┘
```

### 6.2 写方向（记忆沉淀）

| 事件 | 记忆内容示例 | category | importance | 现状 |
| --- | --- | --- | --- | --- |
| 症状初筛 | "2026-08-22 症状初筛：呕吐+腹泻，评估 warning" | medical | 按风险映射（emergency=9 / warning=8 / caution=6 / normal=4） | ✅ 已有 |
| 打卡异常 | "近3天食欲下降，精神差" | health | 5-7 | ✅ 已有 |
| 恢复事件 | "呕吐症状已恢复，历时3天（2026-08-19~22）" | medical | 6 | ✅ 已实现（2026-08-22）：低风险检查 + 14天内同症状高风险检查 → 自动沉淀"已恢复"记忆 |

**写方向规范**：
- 记忆 content 必须含结构化时间戳（供 90 天时间窗与"上次什么时候"召回）
- tags 打上症状 ID/身体系统（如 `tag: vomiting` / `tag: digestive`），供读方向相关性检索
- 同一事件的重复记忆走 UPSERT（现有机制：importance 取大、evidence 合并、confidence +0.1）

### 6.3 读方向（记忆召回闸门）

```
召回条件（全部满足才进入上下文）：
  category ∈ {health, medical}      ← 只读健康/医疗类，忽略 habit/preference/feeding/general
  status = active                   ← 忽略 contradicted / dormant / expired
  importance ≥ 5                    ← 只读有价值记忆
  时间窗 = 近 90 天                   ← 过时记忆不进上下文
  相关性 = content 命中当前症状名/身体系统/关键词
```

**场景化召回（4 类，对应 PRD 4.5.4 的差异化卖点）**：

| 场景 | 触发 | 输出示例 |
| --- | --- | --- |
| 相似病史 | 症状名命中历史记忆 | "📋 上次（3月12日）也出现过呕吐，3天后恢复" |
| 医嘱关联 | 记忆含"医生/医嘱/检查"关键词 + 症状身体系统相关 | "📋 记忆：医生说咪咪心脏有点杂音，本次咳嗽建议尽早就医" |
| 季节规律 | 去年同月同症状记忆 | "📋 去年这个时候也出现过皮肤瘙痒" |
| 恢复参考 | 相似病史 + 有恢复事件 | "📋 上次类似情况 3 天就好了，可参考当时的恢复过程" |

### 6.4 类人记忆的三个特征（设计原则）

1. **双向**：写（自动沉淀）+ 读（相关性召回），不是单向的"记录器"
2. **关联**：按症状/身体系统/时间召回，而不是把全部记忆倒给用户——像人回忆一样"想到了相关的"
3. **遗忘**：已有衰减机制（dormant/expired）+ 时间窗闸门，过时记忆自然淡出（`memoryService.ts` runMemoryDecay 已有）

### 6.5 接口设计

- **读取**：`GET /api/pets/:petId/symptom-check/context`（新增）→ 返回闸门筛选后的健康/医疗记忆 + 近7天打卡摘要；或复用现有 `GET /api/memories`（memory.ts 已有）再由前端做闸门过滤
- **写**：沿用现有 `recordHealthMemory` + symptoms.ts 自动沉淀；新增"恢复事件"沉淀入口（用户结束症状跟踪/恢复正常打卡时触发）
- **失败降级**：记忆接口超时/不可用 → 跳过记忆召回，仅规则+图谱结果照常返回（不阻塞主流程）

### 6.6 与置信度的关系（关键约束）

- 记忆召回的结论一律 `basis='record'`、`confidence=medium`，展示时标注来源"日常记忆"
- **记忆永远不参与 riskLevel 推导**：安全底线由规则引擎独占；记忆命中"医嘱/慢性病"时只触发"建议就医"提示（符合只升不降原则）
- 目的：记忆给分析"人味"和"背景"，但绝不让不可靠的记忆改变"该不该去医院"的判断

## 七、数据来源与审核（不爬数据）

### 7.1 数据来源分级

| 优先级 | 来源 | 用途 | 获取方式 |
| --- | --- | --- | --- |
| P0 | 现有代码资产（CONDITION_MAP、breeds.ts、foodSafety*.ts） | 冷启动主体 | 直接结构化迁移，零外部依赖 |
| P1 | Merck Veterinary Manual（免费在线版） | 症状→疾病映射补充（PRD 9.1 已定） | 人工摘录 + 审核 |
| P1 | ASPCA 毒物清单 / Pet Poison Helpline | 食物/植物安全补充 | 人工摘录 + 审核 |
| P2 | AKC / CFA 品种库 | 品种遗传病补充 | 人工摘录 + 审核 |
| P2 | WSAVA 临床指南 | 疫苗/驱虫时间表 | 人工摘录 + 审核 |

### 7.2 审核流程（沿用 PRD 9.1.3，落到数据结构上）

```
用户反馈错误 → 分类（食物/症状/品种） → 人工核查（对照权威源）
→ 修改图谱条目 → reviewStatus: draft → 人工复核 → reviewed
→ version 递增 → 随发版发布（紧急条目 CDN 热更新）
```

**审核原则（硬约束）**：
- 所有修改必须挂 `sourceRef`，无来源条目 `reviewStatus` 恒为 `draft`，**禁止进入正式输出**
- 症状映射修改必须 Merck 确认；食物修改必须 ASPCA/Pet Poison Helpline 确认；品种修改必须 AKC/CFA 确认
- 置信度上限受来源权威度约束：`community`/`internal` 来源的条目最多 `medium`，不可能 `high`

**种子治理（Phase 3 补充，防数据漂移）**：
- `server/src/data/medicalGraphSeed.json` 是前端 `medicalGraph.ts` 的导出快照，用作服务端权威图谱的**初始版本**（空表惰性播种）
- **修改 `medicalGraph.ts` 必须同步重新生成种子**（一次性导出脚本已用后即删；后续应固化 `npm run seed:gen`），否则 DB 播种后服务端永远停留在旧数据
- DB 一旦播种，后续更新一律走管理后台保存新版本（版本自动递增），不再读种子

## 十一、风险与边界声明

1. **置信度 ≠ 医学准确率**：`confidence` 表示"结论有据可依的程度"，不对外宣称准确率，避免误导。
2. **不做诊断、不推荐用药**：LLM prompt 硬约束 + `guardOutput` 输出检测双保险；护理建议数据层面不收录任何药物内容。
3. **免责声明必须展示**：所有输出入口（页面/聊天/报告导出）沿用 PRD 8.4 模板。
4. **静态 JSON 的局限**：数据量增长后查询与更新会变重，届时按 PRD 9.1 增强阶段评估迁移数据库；当前 MVP 规模（200+疾病、500+食物、250+品种）静态 JSON 足够。
5. **人工审核是上限**：图谱质量的天花板取决于审核频率，Phase 3 的"纠错入口 + 运营后台"是长期质量保障，不是可选项。
6. **记忆质量依赖 AI 提取**：记忆引擎的记忆由 LLM 从对话中提取，存在误记/矛盾可能（已有 contradicted 状态兜底）。召回仅作背景展示、不进 riskLevel，把记忆错误的伤害面压到最低。

## 附：一句话总结

**规则引擎保证不犯错（安全底线），知识图谱保证有依据（置信度来源），记忆引擎提供类人背景（双向读写、只作展示不作判断），LLM 保证有温度（话术包装）——四者叠加，置信度可解释、可测试、可见证；数据全部来自现有资产 + 权威源人工整理 + 记忆引擎召回，不爬取、不做诊断、不推荐用药。**
